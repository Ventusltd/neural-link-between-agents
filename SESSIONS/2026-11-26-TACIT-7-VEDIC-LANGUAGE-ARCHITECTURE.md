## 3. Probabilistic Python distillation: design hypotheses, measure them
Implement one Python pipeline over the existing producer snapshot, not 478,404 isolated model prompts. Unit of candidate meaning is a functional family, exact element, bounded sub-body or composition, not an individual physical line. Treat the unique line inventory as an evidence universe. Use all numbered lines as contextual evidence where relevant, never count each line as a meaning. Start with existing 766 standalone candidates, 738 blocks and 253 Vedic function nodes as overlapping priority pools. Eventually process all 33,183 families including unclassified ones; preserve occurrences and expose coverage.

### P0: Corpus adapter and provenance
Reuse tools/modular_snapshot.py and TestCode PR27. Consume verified SQLite asset metadata, compressed/decompressed digests, ordered little-endian line IDs, immutable occurrences and formal producer parse results. Validate against Git blob reconstruction. Compare two real pinned snapshots and JS unpack(), rebuildTablet(), elementSource(), find-prior.mjs; report missing snapshot blocker rather than fabricate replay. Produce compact candidate feature records with family/element/tablet/line IDs where exact. Resolve Kuiper only via existing map; unknown null. Distinguish history and current app edition. Cache by source fingerprint + parser/model revision, not name. Incremental changes only; never rescan all repos when producer has already indexed them.

### P1: Extract multi-view features
Use existing Acorn JS parser/AST and dependency results; Python ast; DOM parsing with BeautifulSoup; optional Tree-sitter where genuinely missing. Collect identifiers split by case/underscores, documentation, existing VEDIC labels, import/call edges, formulas/operators and literal constants with units, parameter/return shape, DOM IDs/events, SQL and API literals, globals/read/write effects, data schema and error behavior. Keep syntax facts distinct from interpretation, and account for nested scope/dynamic calls. Source strip is forbidden: flag CSS/templates/duplicate boilerplate for ranking/index views only. Hash/measure exact original bytes. Deduplicate by producer structural identity while preserving every distinct sense/occurrence and source trace.

Represent the corpus as sparse features with a reproducible Python baseline: TF-IDF/BM25 for names/comments/curated descriptions, AST or structural tokens, and graph-derived features for caller/callee/application context. Use a small interpretable probabilistic classifier (multinomial naive Bayes or logistic regression) for estate group, discipline and VEDIC class hypotheses, trained only on known labels. Model probabilities are estimates, not proof. Cross-validate by family and repo/edition groups to prevent near-duplicate leakage. If labels insufficient, use similarity scores and mark UNCALIBRATED rather than call scores probabilities. Start with standard Python + NumPy/scipy/scikit-learn where justified; pin dependencies, measure memory/time before considering CuPy. No mandatory GPU.

### P2: Probabilistic meaning induction and clustering
Combine lexical, structural, mathematical and graph signals. Example initial ranking hypothesis: 0.35 lexical + 0.25 structure + 0.20 dependency-neighborhood + 0.20 application/domain context; normalize components, log missing features, tune with held-out human labels. These are design weights, not measured optimum. Use sparse nearest-neighbor retrieval / inverted index to avoid quadratic all-family comparison; cluster only as suggestions with cluster exemplars, alternative senses and conflict evidence. Graph propagation from curated meanings may suggest labels for connected functions but must not claim inferred labels verified. Use uncertainty/margin and out-of-distribution detection to abstain, prioritizing uncertain/high-impact cases for review. Avoid grouping by shared word alone (e.g. AREA circle vs polygon; electrical CURRENT vs time-current). Distinguish similar source from equivalent functionality. Evaluate top-k retrieval, precision/recall, false merges, calibration/Brier where valid, abstention and coverage; publish test set and error examples. No invented confidence numbers.

### P3: Two-pass translation and active learning
Build a compact evidence packet per candidate: immutable source span, producer identity, signature, typed/observed inputs and outputs, direct dependencies and selected callers, application context, source-data vs model distinction. No entire monolith or indiscriminate raw corpus in prompt. Pass 1 mechanical mapping: exact inputs, formulas, conversions, branches, side effects, dependencies, outputs and constraints, cite range for each. Pass 2 operational synthesis: what, why in the electrical/energy workflow, explicit limits; propose verb/meaning, taxonomy, aliases, typed ports and related capabilities. Python can generate mechanical templates and probabilistic label suggestions; it cannot be assumed to understand arbitrary code intent from syntax alone. For difficult or ambiguous cases use owner-approved LLM build-time translation or human review; no credentials/API budget assumed, no external model calls from static browser. Structured schema, prompt/model revision, source hashes, evidence and review state. Never promote probability alone to verified meaning. Review ten at a time and feed verified labels back to the classifier. Compare deterministic reruns. Do not claim 33k semantics until reviewed.

### P4: Semantic twin ledger and index
Keep existing data/dictionary.json immutable identities; versioned additive sidecar keyed by gg_id and contract revision/source key. Candidate labels separate from allocated IDs. Entry includes estate group -> discipline -> VEDIC class, application aliases/edition, capability, composition and connected knowledge. Source pin + span kind (whole function/class/sub-body/file/composition), byte/line count, SHA256, parent/column bounds, licence, producer keys. Pass 1 mechanical facts and Pass 2 operational prose separately. Ports: name/type/unit/shape/schema/cardinality/bounds/nullability; global/DOM/data/library dependencies, network, side effects, errors, licence. Output classification VERIFIED_SOURCE_DATA or ILLUSTRATIVE_INDICATIVE_MODEL, or UNVERIFIED where missing; source data does not validate model output. Independent evidence states for byte verified, static, producer join, fixture, actual runtime, hosted CI and served bytes. Publish small manifest/index shards or Parquet/DuckDB client-side where measured appropriate. No raw source duplication, no cookies, telemetry or backend. Priority hot items first, not sorted by arbitrary probability alone.

### P5: Conversational VEDIC language (intent-to-composition)
Design a constrained intent grammar, not a new general-purpose runtime:
- User phrase -> intent frame: action, domain object, parameters/units, constraints, required output, application context, evidence and uncertainty.
- Search existing words, aliases, purpose, ports, taxonomy, dependencies, model limits. Return ranked senses and source pins. Clarify only consequential ambiguities (e.g. MW vs MVA, location vs identity, map distance vs actual route). Retain previous conversation selections with explicit version pins.
- Resolve selected meaning to deterministic immutable source and producer identities. If missing, offer related candidates; never invent a key.
- Plan a DAG of capability IDs with explicit ports, order/parallelism, data flow and adapters. Graph search/beam search can rank candidate plans by semantic fit, reuse, adapter cost, dependency completeness and uncertainty; hard constraints filter before ranking. Unknown inputs, units, licences, unavailable libraries/data, global state conflicts, output schemas, circular dependencies and side effects block automatic execution. No arbitrary evaluation of conversation or untrusted code. Candidate plan may be described but not called executable.
- Retrieve exact existing source via Git and existing Stars retrieval. Minimal glue only; no rewrite of proven domain maths. Use explicit adapters for conversions; test known answers and negatives in isolation. Do not execute arbitrary remote source or mutate live apps. Present plain English plan and evidence, then a tested static modular candidate where scope permits.
- User can iterate conversationally; update plan while preserving immutable references and test history.

Example (design only): 'Show me a proposed 100 MWp solar site, nearby substations, straight-line distance and indicative cable losses.' Resolve solar plant sizing, project coordinate selection, existing vicinity/nearest and geodesy capabilities, then electrical losses. Require voltage, current/phase, conductor resistance/temperature and length assumptions for loss; do not infer grid capacity or route. Ask only missing material inputs; outputs labelled source data vs indicative model. Separate map straight-line distance from cable route. Verify exact compatible ports and dependencies. No actual electrical design or connection approval.
Second example: 'Find a project by postcode, show the location and calculate bearing/distance to a selected point' -> actual GridAtlas selection + existing ORIENT composition (shared inputs); ensure coordinate order and degrees, known-answer regression. These are acceptance scenarios, not claims of existing assembled applications.
