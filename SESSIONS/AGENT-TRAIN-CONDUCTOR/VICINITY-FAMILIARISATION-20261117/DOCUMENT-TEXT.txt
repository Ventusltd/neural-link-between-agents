Vicinity Familiarisation (London-Style Grid Explorer)
【48†embed_image】 Figure 1: London Underground map (CC-BY-SA) as inspiration for a grid “train journey” UI. We envision a new Vicinity Familiarisation layer in GridAtlas that lets a user pick a “station” (substation/offtaker) and draw a contiguous path through the real grid network, much like tracing a tube line. The UI would include a radius slider (1–50 km) and selectable voltage bands (e.g. 400 kV, 132/66/33 kV, 11 kV), and present results in neon-highlighted “route” overlays. For example, a non-expert could choose a local substation as Start, then “Add Destination” to another substation; the tool computes all connected edges between them within the radius. Branch points (transformers, circuit splits) would be shown as interchange “stations” (with icon legend for transformer size/turn ratio), and voltage changes (400→132→33→11 kV) marked by distinct colors or symbols. Multiple visual modes (neon polylines, Kuiper sunflowers, Faraday ripples, lightning flashes) would be offered as toggles under a new “Grid Journeys” heading in the existing GridAtlas layers plugin. Crucially, geometry always snaps to surveyed asset locations (pylons and underground cable routes) if available; otherwise straight-line connectors may be used with an “unverified” badge. The interface emphasizes “candidate” (non-validated) exploration, with clear labels for confidence and data source. (See Appendix for mock-ups.)
Data & Legal Sources
The feature relies on real network topology where available. For the 400 kV and 132–275 kV transmission network, Ordnance Survey’s OpenMap – Local provides overhead line geometry under OGL v3.0【30†L281-L290】. OS defines “ElectricityTransmissionLine” as cables on pylons (suspended lines)【30†L281-L290】. For example, OS maps 11,831 line segments (c. 7,575 km at 330–549 kV, plus 6,373 km at 220–329 kV) across GB【62†L42-L50】. These OS lines (EPSG:27700) give a public baseline for high-voltage corridors. In contrast, much of the distribution network (≤132 kV, especially 10–33 kV lines) is not open from DNOs. National Grid Electricity Distribution (NGED, ex-WPD) provides a Tabular LTDS model (Extra High Voltage 132/66/33→11 kV) as CSV under OGL【22†L22-L30】, which enumerates circuits and transformers. NGED also publishes a Distribution Substations list linking each 11 kV substation to its higher-voltage “primary” supply【28†L17-L25】, and detailed substation loading tables【26†L17-L25】. These NGED tables can anchor the network graph (node IDs) but lack GIS geometry. For actual cable coordinates below 132 kV, we fall back to OpenStreetMap/OpenInfraMap data. OpenInfraMap reports ~199,900 km of mapped power lines in the UK (OSM contributors, ODbL)【62†L42-L50】. Notably ~30% of these (60,279 km) are tagged 10–24 kV, 16% (31,682 km) as 25–51 kV, etc.; 36% of OSM lines have no voltage tag【62†L42-L50】. OSM/InfraMap thus provides extensive local distribution geometry (e.g. pole or duct routes), albeit volunteer-quality. Any use of OSM data must attribute the ODbL license and acknowledge incomplete tagging【62†L42-L50】【62†L58-L61】.
Where possible we also use official flow/asset data for context (though not to display flows as live). For example, National Grid ESO’s ETYS (Electricity Ten Year Statement) includes schematic transmission topology and simulated flow arrows. Elexon’s Balancing Mechanism Reporting Service (BMRS) provides half-hourly actual generation and demand by region (accessible by API) to validate route importance. Many UK power networks (e.g. UKPN, SSEN, SPEN) have partial Open Data portals. SSEN’s “Electric Office” GIS data (shared classification) covers circuits from EHV to LV but requires prior approval and warns that its maps “cannot be relied upon as they are indicative only”【20†L16-L24】. We would not host restricted data; instead we note such warnings to users (e.g. “indicative only”).
Importantly, NUAR (National Underground Asset Register) is off-limits as public data. NUAR is a secure, invitation-only service (currently asset-owners and their contractors) for safe digging【18†L81-L89】. Its terms explicitly forbid commercial/planning uses (“determining best locations for new assets” or “network expansion”)【18†L141-L149】. We do not promise underground 11 kV routes, nor ship any raw NUAR data. Instead we design a permission-gated adapter: Ventus engineers may manually query NUAR via official API (if licensed) and import only summary results (e.g. “substation X is connected to GIS nodes”). The public UI will show user-submitted “unknown” routes only as dashed or question-marked lines, subject to later verification. All open-source data (OS, OSM, NGED) will be credited (in legend/tooltips) and used under their licenses【30†L281-L290】【62†L42-L50】.
Architecture & Integration
This feature builds on existing Ventus GridEngine and GridAtlas map layers. Conceptually, we overlay a network graph (nodes=substations, edges=circuits) atop the MapLibre map. Geometry comes from either OS lines, OSM polylines, or straight connectors if needed. The graph is pre-computed (in ventus-grid-engine) using NGED/LTDS and any other available topology. We will reuse the existing network-topology.js and electrical-distance.js modules for finding connectivity. A bounded-edge-cover or shortest-path algorithm (backtracking through branches) will enumerate all contiguous routes from the origin node within the radius, respecting topology (no cyclic loops) – this builds the “journey”. The resulting sequence of substations and transformer connections is rendered as a neon polyline overlay (LayerGroup) via GridAtlas’s Layers plugin. New code under gridatlas/src/layers/ will define a “Vicinity Journeys” layer type with UI controls (origin picker, radius slider, voltage filter toggles) and tooltips (show substation name, voltage, evidence badge).
Key design points: “Observed vs Theoretical” – if a connection is known (OS/NGED/OSM), we draw it solid; if only proposed or historical, we draw it dotted and mark Candidate. Map interaction remains smooth: we cap the maximum features to avoid performance issues (e.g. a 50 km radius might cover hundreds of lines, so implement lazy rendering or simplify lines at zoom). We will not change any backend data sources (the canonical REPD or Solar1000 tables remain fixed); this is purely a UI overlay. All new APIs will be internal: e.g. GET /api/journeys?origin=ID&radius=km returning JSON of node IDs and coordinates. Existing Ventus services (e.g. off-takers “vicinity” endpoint) may be repurposed to list nearby substations, but the core algorithm resides in a new GridJourneyEngine module in ventus-grid-engine repo. No live homepage promotion or unintended SEO content: the UI will label all this as exploratory only.
Incremental Deliverables
We propose five overnight deliverables (D1–D5), each testable and rollback-safe:
D1: Radius-Based Network Query. Scope: Add UI to select a center point (substation or address) and radius. Query the Ventus off-taker database to list all ≥33 kV substations and generation within that radius (similar to existing 30/30/30). Store these nodes as graph input. Render initial “star” lines from the center along visible edges. Tasks: New vicinity-tool React component; backend findNodesInRadius. Use existing map styling (polyline color by voltage). Acceptance: Unit tests for radius filter (known cases), integration test that radius=0km returns none, radius covers known sample set. Verify map draws only within radius (screenshot). Negative tests: Out-of-bounds radius defaults to max 50 km; invalid inputs show error.
D2: Voltage Layer Filters & Legend. Scope: Implement checkboxes for voltage classes (e.g. 400 kV, 132/66 kV, 33 kV, 11 kV) in the new layer UI. Toggling these should hide/show the corresponding route segments. Add a legend labeling colors (e.g. red=400kV, orange=132kV, yellow=33kV, grey=11kV). Tasks: Extend gridatlas layer config, update polyline style rules. Add descriptive labels/tooltip for each voltage. Acceptance: Confirm that only selected voltages appear. Programmatic test: given a mixed-route polyline set, filters remove correct subset. UI snapshot shows legend. Negative: Nonexistent voltage codes are ignored, checkboxes disabled if no data.
D3: End-to-End Path Exploration. Scope: Enable selecting an origin and destination node. The engine computes the network path (all branches) connecting them within radius. This is more than a straight arrow – it may traverse multiple substations. We will run a depth-first traversal limited by distance (logical hops or weights) to cover all edges that connect origin→destination. If no explicit destination is chosen, default to full network coverage from origin. Tasks: Enhance GridJourneyEngine with a DFS/BFS on the subnet graph. Integrate with UI: two clickable substation markers (origin/dest). Mark the route path nodes in sequence. Acceptance: Automated test: known small graph returns expected path (we’ll include a synthetic 4-node test). In UI, selecting node A then B highlights the chain (screenshot). Check mobile (Chromium/WebKit) that map expands to show path. Negative: If dest unreachable or same as origin, show “no path”.
D4: Visual Modes – Kuiper/Faraday “Sunflowers” and Lightning. Scope: Add toggles for alternate visualization overlays. Kuiper mode: reinterpret connections in a polar “sunflower” pattern (like Vogel spirals) around the origin, using the user’s custom radius. Faraday mode: animate a wave/ripple emanating from origin following edges. Lightning mode: momentarily highlight major junctions with a flash effect. These are cosmetic; network connectivity remains same. Tasks: Integrate Ventus globalgrid2050 “kuiper-grid” module for radial layout. Write simple CSS/JS animation effects. Provide “Neon” CSS class. Acceptance: Each mode toggle must visibly change the map (e.g. Kuiper shows points in spiral, Faraday shows pulsing circle). Automated check: CSS classes applied correctly, no JS errors. User test on mobile confirms toggles work (no new data fetch). Negative: Modes off by default; if WebGL/CSS3 unsupported, fall back to default line.
D5: User Feedback & Suggestions Pipeline. Scope: Implement a confidential “Suggest a Missing Line” form. Users can draw (or select) a proposed new segment and submit it. Submissions go to a private Ventus queue (e.g. a secured Google Sheet or internal API). No public map update on submission. We’ll add a special “Feedback” status badge for any uncertain connection (dashed line, “Needs verification”). Over time, accepted suggestions can seed future data. Tasks: Add a “+” button in layer UI that lets a user click two points to propose an edge. Build a backend endpoint to record submissions (with CSRF protection). Flag feedback lines in map overlay. Acceptance: Survey form submits test data, appears in private log (dummy auth). New lines appear grey/dashed on map only after marking from admin panel (mock this). Ensure no raw location data leaks to public. Negative: Form cannot submit outside radius or duplicates (show alert).
Each deliverable has its own feature branch. Automated CI jobs will run targeted unit tests (e.g. Jest for engine logic, Puppeteer for map render) and separate QA checklist (mobile viewport, browser compatibility). We require independent sign-off (e.g. by Codex Agents 2–4) before merging. Rollback is easy: each feature adds new code only, existing map/layers remain unchanged.
Task Breakdown & 1-Night Plan
Ten ordered tasks are assigned to up to eight Codex agents, with disjoint worktrees and no overlapping edits (especially avoiding concurrent changes to atlas/current.json). Each task is standalone & commit-ready:
Agent1 – Data Modeling (Backend): Create a new GridJourneyEngine class in ventus-grid-engine repo (branch GJ-pathplan). Ingest NGED LTDS tables and OSM/OS data into an internal graph (node/edge list). Write parsers to link distributions to primaries (using Tables from【22†L22-L30】【28†L17-L25】) and label each edge with voltage. Test: On sample CSV data, verify graph edges count and connectivity.
Agent2 – Radius Selector UI (Frontend): In gridatlas repo (branch GJ-ui), add a new layer module (e.g. vicinity-familiarisation.js). Agent3 – Path Algorithm (Backend): In GridJourneyEngine, develop the actual path-finding logic. Using the graph from (1), write a deterministic DFS/BFS that, given origin (and optional destination), returns all reachable node IDs and edges. Weight edges uniformly (or by physical line length if geodata available). Export an API endpoint in gridatlas-backend like /api/v1/journey?origin=X&dest=Y&radius=Z. Test: Provide a small mock graph; assert that GET /api/journey?origin=A&dest=B yields the expected edge sequence (unit test). Check the API handles invalid IDs gracefully (404).
Agent4 – Map Rendering (Frontend): In the vicinity-familiarisation layer code, consume the journey API. Convert returned coordinates into a MapLibre polyline layer. Agent5 – Filters and Legend (Frontend): Extend the layer UI to include voltage checkboxes and an on-map legend. Agent6 – Visual Modes (Frontend): Integrate the Kuiper “sunflower” visualization. Agent7 – Feedback System (Backend): In gridatlas-backend, add a secure feedback endpoint and DB table. On receiving a {fromNode, toNode, userId (optional)} payload (after UI draw), store it in a suggestions table with timestamp and status “pending”. Do not broadcast these to public outputs. Modify the journey response to mark any edges flagged “pending” with a special flag. Test: Simulate form submission with a valid edge; confirm it is recorded. Then simulate an admin confirmation (change status to “approved”) and verify the next journey render includes it (marked differently).
Agent8 – Licensing & Data Audit (Documentation/Test): Compile a spreadsheet of all data sources, their licenses, and how they’re used. Each step’s output is self-contained: feature branches allow rollback. No single step changes live atlas data; all merges simply add new code. User Feedback Pipeline (Unknown Routes)
To crowdsource missing links safely, we implement a Feedback mode as above (Deliverable D5). Key points: any user-submitted “invisible circuit” is stored privately; on-map it appears only after manual validation by Ventus engineers. This uses an opt-in reporting form – not a live wiki. Each suggestion is anonymous but timestamped. Moderators will follow a privacy-first workflow: no GPS data of buried cable is exposed to casual users, and any display of an “unknown” route is flagged (e.g. dashed red line with “Needs confirmation”). We explicitly disallow ANY automated inclusion of user data into the official grid graph. Moderators (using a secure admin interface) can verify with asset owners or licensed maps (e.g. after cross-checking NUAR internally) before marking a route “Confirmed” or discarding it. This ensures no crowdsourced rumor becomes part of the published map without evidence. The feedback queue (and any metric of volume) stays within Ventus’s secure systems – we do not publish it. Users see only the vetted result (or the “candidate” badge).
Integration with Faraday/Kuiper/See-Through/Solar Design
We will reuse Ventus open-source modules where possible. For example, the Kuiper “sunflower” visualization (in globalgrid2050/kuiper-grid) provides spiral layout code; we will adapt its algorithms for the Kuiper mode above. Similarly, Faraday experiments (pulse-propagation code) inspire the ripple animation. The See Through app code (if present in Ventus GitHub) can guide semi-transparent 3D effects, though we only need 2D overlays here. The Solar Design Studio toolkit (in globalgrid2050/solar-design-studio) contains rendering primitives and GUI patterns; we’ll copy any reusable components for the dashboard view.
Each integrated piece will retain its license and attribution. For example, OS data is OGL (attributed in UI), OSM is ODbL (we display a logo per requirement【62†L58-L61】). If any external lib (e.g. OpenLayers, React components) is used, it’s already in the repo with compatible license. Conceptual example: one mockup shows a “Sunflower” mode toggle. Clicking it rotates the origin node’s edges 137.5° apart (Vogel’s sunflower angle), drawing wires as petal-like spirals (a nod to Kuiper’s generative pattern). Another mock shows “Faraday” mode: a concentric ring animation propagates outwards along the route, as if a field pulse moving through the network. These enrich the educational feel but are purely illustrative. In all cases, original source code (in Ventus repos or third-party) is simply invoked, not re-implemented from scratch.
QA, Security, Accessibility, Releases
Security: No sensitive data is exposed (see NUAR FAQ【18†L81-L89】). We do not store any personal info from users (the feedback form is anonymous except for user-chosen labels). All new APIs are behind the existing Ventus origin whitelist and use HTTPS. The feature does not request new permissions (no user login needed). We will run static analysis on the code to check for vulnerabilities.
Data Provenance: Every route shown will carry tooltip captions like “Data source: [NGESO, NGED, OSM]”. Any “candidate” or “suggested” link has a disclaimer (“not confirmed”). This guards against misinformation (we explicitly do not animate real-time flows, avoiding any implication of actual power transmission or fault status).
Performance: The layer will load only on demand. We will lazy-load edge geometry (vector tiles) and simplify lines for large radius. Acceptability is defined as a full 50 km query drawing ~1000 edges loading in <3s on mobile (we will test on Chrome and Safari on iPhone simulators). The code will be benchmarked against the existing Offtakers drill-down (which already handles 100–200 points smoothly).
Accessibility: The layer respects color contrast guidelines. Voltage filters will have aria-labels, and the map is keyboard-navigable. We ensure any animation can be turned off (prefers-reduced-motion). All legends and tooltips use clear language (e.g. “132 kV AC line”).
Licensing: OS data (Figure 1 example) is OGL【30†L281-L290】, attributed in UI. OSM data is ODbL【62†L58-L61】; we must include an attribution link (done in the base map). NGED data is OGL【22†L22-L30】; copyright notes will appear in release notes. We verify that none of the SSEN “Shared” or NUAR data leaks out.
Release Checklist: Before release: all unit tests passing; all code reviewed (no leftover console.log); no console errors in the browser. Mobile QA: test on iOS/Android browsers (focus on the known “first tap to open map” bug – ensure our MapLibre popup opens on first tap as fixed in V9.22【1†L31-L36】). Accessibility audit (Lighthouse) score ≥90 for the new layer section. Legal sign-off: ensure that use cases comply with NUAR limits (safe-dig only), highlight in docs that this is for education and planning only. A rollback plan (delete new layer code) is included.
Open Questions / Decision Points
DNO Data Coverage: Can we obtain any more precise 11 kV or LV GIS data? (Most DNOs rely on Linesearch before works【20†L16-L24】.) If not, the UI must caution that very local links are speculative.
Public NUAR Access: Officially NUAR is invite-only【18†L81-L89】, but the user asked for NUAR integration. Will Ventus apply for sandbox access for this feature? Or must we wait for 2026/2027 expansions? We assume only asset-owner mode and treat NUAR as offline manual verification.
Routing Ambiguity: The requirement “trace all possible grid routes” suggests multiple branches. Our design picks the simple path (no loops). Is that adequate, or do we need to also show parallel circuits? If parallel routes exist (meshed grid), should we display them too? We propose only the primary path by default (like a tube line has one line), with an option to show “alternate routes” (requires advanced path-cover algorithms).
UI Complexity: Displaying every small branch within 50 km could be very busy. We might need “zoom-level threshold” (e.g. only show 132 kV+ lines unless user zooms in) or clustering. The user did not specify this; should we include it now or flag it as future work?
Integration Order: We must avoid merging code that touches atlas/current.json concurrently. Likely Agent8’s licensing/docs task and Agent9’s CI config can go early, while Agents 1–7 incrementally add functionality.
Mobile Bug Legacy: The V9.22 fix for the “first-tap hidden map” bug【1†L31-L36】 must be verified as still in place (we’ll double-check after implementing the new overlays). If regressions occur, that becomes a blocker for merge.
In summary, this design turns the map into an explorable “metro map” of the grid, leveraging open data (OS, OSM) and existing Ventus tools while carefully respecting legal limits (no raw NUAR lines, no misrepresenting data). The result is an educational feature for students or planners to “ride the grid” in a 1–50 km bubble, complete with cute neon graphics and clear evidence labels. All specifications above are grounded in current repos (see [OS and NGED data sources] and [NUAR rules] cited) and split into safe, testable increments with independent review.
