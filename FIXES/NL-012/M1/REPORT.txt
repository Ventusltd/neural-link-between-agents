How the job decides (by sha256, never by URL):
- It downloads the newest CSV and XLSX the content API links to. If the content API fails, it reads the publication page instead.
- If both hashes are already pinned in automation/repd/releases/*.json, the run is green with "No new REPD release". This is also what
  happens when GOV.UK redirects an old URL to a replaced file.
- If the bytes are new, it derives the release id from the file name or title; if neither names a quarter, it uses the last quarter
  ended by the publication date. It then:
  * writes releases/<id>.json and releases_v6/v6_<id>.json, with counts computed from the downloaded bytes;
  * carries the previous release's acceptance waivers forward;
  * adds allow-list lines for dist/project_identity_<id>.json, dist/repd_master_<id>.json and
    uk_renewables_pipeline/<stamp>/fixtures/<id>/project_identity_<id>.json;
  * runs run.py --offline on the same bytes;
  * opens the pull request. Its body holds the summary, the change report and the run report.
- If the bytes are new but the id already has a descriptor (a correction), the run goes red for a person and writes nothing.
- If the branch already exists (an earlier pull request is still open), the run is green and nothing is pushed.
- The deviation: no date-stamped label. run.py, config.py and the V6 scripts accept only 20xxqN, so the date fallback gives a quarter id.
