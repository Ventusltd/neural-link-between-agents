WHAT IT DOES
- Reads 9 fixed public feeds (list below). Keeps a headline when the headline or the feed summary names a data-centre
  term (data centre/center, datacentre, hyperscale(r), AI infrastructure, AI growth zone, compute, supercomputer, or
  a site or data-centre operator from the register) AND
    capex lane:    investment, capex, capital expenditure, spending, billion/bn, million/m, funding, build,
                   construction, expansion
    politics lane: planning, council, grid connection, connection queue, National Grid, NESO, Ofgem, minister,
                   government, MPs, bill, legislation, parliament, consultation, growth zone, energy prices/costs,
                   water
  An item can be in both lanes. Stored per item: title, link (tracking parameters removed), source, date (UTC, or
  null when the feed gives none), first_seen, lanes, matched_terms, sites, site_matches. The feed summary is read
  in memory only for matching and is never written. No article page is requested.
- Deduplicated by canonical link; merged with the previous file so stories survive rolling feeds; newest 200;
  ordering: dated items newest first, then undated, link as tie-break. Two runs on the same input give
  byte-identical files (tested).
- Register join: when the HEADLINE names a register site name (or alias) or operator, the register id (dcuk-...) is
  attached, at most 5 per item, site-name matches first. Generic names ("Unnamed data centre") never match;
  short upper-case operators (SCC, NTT) match case-exactly; AWS/Amazon alias for Amazon Web Services. Naming a
  general company that also runs a register site (Microsoft, banks, telecoms) attaches the sites but does not by
  itself make the headline a data-centre story.
- REPD context per attached site: live REPD solar, battery, onshore and offshore wind projects within 10 km
  (count, stated MW, by technology, projects with blank MW counted separately as unknown) from
  dist/convergence/2026q3/datacentre_proximity.json (Team 6, on main). Null when the register point is not
  proximity-reliable. Labelled on the page as straight-line context, not a connection.
- Failure: each feed is fetched separately; an error (network, HTTP, bad XML, DTD/entity, >2 MB) is recorded in
  "feeds" and the run continues. The job fails only if every feed failed and there is no earlier file.

WORKFLOW: WHY A DATA BRANCH (three sentences)
The workflow writes dist/datacentre_news.json to its own branch, datacentre-news-data (an orphan branch holding
only that file and a README), and the panel reads it from raw.githubusercontent.com with the site's own
../../dist/datacentre_news.json as fallback. This keeps daily bot commits off main, needs no PR or PAT, and needs
no Pages deploy: deploy-pages only publishes on pushes to allow-listed paths, dist/datacentre_news.json is not on
that list, and pushes made with GITHUB_TOKEN start no workflow anyway. The page change itself (0002/0003) is
inside a release folder, which is on the deploy allow-list, so it goes live with the ordinary merge.
