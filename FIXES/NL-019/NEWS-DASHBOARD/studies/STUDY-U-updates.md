# STUDY U: why Pipeline News does not update, and the smallest fix

Agent U, 14 November 2026, 10:04 to 10:30 UTC. Page studied: `uk_renewables_pipeline/202611140306/` (V9.20) at main `4912c6c1`. Read-only; nothing committed or dispatched.

## Diagnosis

The main newspaper is a file last crawled on 22 August 2026 and it cannot change: nothing writes it (the three crawler workflows were switched to manual on 23 August, and the last scheduled run failed), and every release runner now pins its SHA-256, so rebuilding it would fail the release checks. The page then hides the age: the masthead says "ENERGY DAILY", the header count "133 HEADLINES · 45 UK · 19 INTERNATIONAL" is typed into `index.html`, and the one line that used to carry the feed date is overwritten with "audited snapshot". The NEWS SIGNAL column is computed from the same August file, so it marks 29 of 7,775 rows and links to nothing. The register-changes list and the regional list are frozen copies inside the release folder. The newer feeds from PRs #66 and #67 are on main but no page script reads them. Only the data-centre panel is built to refresh itself (data branch, read through raw.githubusercontent.com), and it has so far run by hand only: its first scheduled slot produced no run. The fix is to copy the data-centre pattern for the main headlines, in one last release, and have the page state the feed's age itself.

## Root causes, in order

1. **The feed the page reads has no writer and may not be rewritten.** `tests/check_v9_20.mjs` line 80 (from `automation/pipeline_release/check_template.mjs`) asserts the SHA-256 of `dist/major_project_news_v9_5_1.json` is `cea104c3…` with the message "must not be rebuilt by this release". Any scheduled job that refreshed that file would turn every release runner red. The loader also demands fixed fields (`v9_4_baseline_headline_count === 125`, line 106).
2. **The crawlers stopped on 23 August and were never replaced.** Commit `3bcb1252` ("V7: retire legacy writers") set V4, V5 and V6 to `workflow_dispatch` only. Last scheduled runs, all 23 Aug: V4 `32621259973` success; V5 `32621092076` failure at "Validate generated newspaper before publication"; V6 `32621379438` failure at "Pass 3 scope audit", log line "V6 AGREED-SCOPE VALIDATION FAILED - homepage V6 snapshot wording". A homepage wording check, not a news fault, stopped the last crawl.
3. **The page hides the age.** `index.html` line 79 hard-codes the counts; `newspaper-v9-7.js` line 79 replaces the dated line with "… 133 headlines · audited snapshot". A reader sees "ENERGY DAILY" over stories dated 2026-08-21.
4. **New news work landed as files, not as something the page reads.** PRs #66 and #67 added about 4.5 MB under `dist/` that no script in the release folder fetches, and their articles are the same August set.
5. **The one live feed is unproven and thin.** `datacentre-news.yml` has 4 runs (`43539485129`, `43539808173`, `43545879645`, `43549425594`), all `workflow_dispatch`. The 05:23 UTC slot on 14 Nov, four hours after the file reached main, had produced no run by 10:04, while other scheduled workflows in the repository ran at 05:56 and 06:11. Its fallback `../../dist/datacentre_news.json` does not exist on main, so if raw is unreachable the page makes a same-origin 404, which the release browser check counts as a failure.
6. **Release folders are immutable, so anything copied in is frozen.** That is correct for the register and the MAP links, and wrong for news.

## Simplest fix (six steps)

One live file on the existing data branch, one small plugin, one last release for news plumbing. `dist/major_project_news_v9_5_1.json` is not touched.

1. **Writer.** Add `automation/news/pipeline_feed.py` and `automation/news/tests/test_pipeline_feed.py`, by the pattern of `datacentre_feed.py`: a fixed list of public RSS/Atom feeds, a keyword filter (solar, battery storage, wind, interconnector, with a UK term), headlines and links only, newest 60 kept. Output `dist/pipeline_news.json`, schema `globalgrid2050.news.pipeline-headlines.v1`, with `generated_at`, per-feed status and `items` (title, link, source, date). No project matching: a headline never carries a REPD Ref ID, so any binding would be name-only. The feed URLs could not be tested from this sandbox; the first manual run's per-feed table settles them.
2. **Schedule.** Edit `.github/workflows/datacentre-news.yml` only: run the new script after the existing one, publish both files to `datacentre-news-data` (keep the branch name, V9.20 reads it), and change the cron to `23 5,11,17 * * *` so one dropped slot costs six hours, not a day. No push to main, no Pages deploy, no new exception to the workflow freeze.
3. **Page, one release (V9.21) through `new_version.py create` / `finalize`.** New `scripts/plugins/live-news.js` (classic `defer` script): fetch `https://raw.githubusercontent.com/Ventusltd/globalgrid2050/datacentre-news-data/dist/pipeline_news.json` with `cache: 'no-cache'` and a 5 s timeout; on failure read `news/pipeline_news.snapshot.json`, a copy frozen into the folder at release time. Put the snapshot outside `data/` so `data_changed` stays false; it is same-origin and exists, so the "no failed same-origin requests" check holds. The folder is 15.78 MB against a 17 MB budget, so keep the snapshot under 100 KB. In the same release change the data-centre plugin's second source to an in-folder snapshot for the same reason.
4. **Honest age, computed in the browser from `generated_at`.** In `index.html` replace the typed counts on line 79 with `<div class="status" id="newsStatus">`. The plugin writes one of: "NEWS UPDATED 14 NOV 2026 05:24 UTC · 37 HEADLINES"; "NEWS STALE · LAST UPDATED 9 NOV 2026 (5 DAYS AGO)" in amber once the file is over 36 hours old; "LIVE NEWS UNAVAILABLE · SNAPSHOT OF 14 NOV 2026". The page never depends on the workflow to report its own failure. Relabel the August list "ARCHIVE · PROJECT-MATCHED HEADLINES TO 21 AUG 2026" instead of "ENERGY DAILY"; whether it is collapsed is the clutter decision.
5. **Leave alone, to protect MAP and the checks.** Do not edit `app-v9-8.js`, `projects-v9-8.js`, `atlas-receiver-v9-7.js`, `#tbody` rows or `a.atlaslink`: check 5 compares every MAP link with the parent character for character. Keep these exact strings in `index.html`, which the inherited feature checks and `check_template.mjs` search for: `<section class="newspaper">`, `scripts/plugins/datacentre-news.js`, `scripts/plugins/register-changes.js`, `href="../versions.html"`. If the August archive is removed rather than relabelled, declare it in `removed_features` as V9.20 did. Do not read the feed through jsDelivr (branch files are cached for hours) or through a site path (each update would need a Pages deploy, and a `GITHUB_TOKEN` push starts none).
6. **Test.** Offline pytest with fixtures for the writer, run in the workflow before fetching. Three `browser_probes` in `registry.json` for V9.21: `#newsStatus` contains "UPDATED" or "SNAPSHOT"; with `block: ["*pipeline_news.json*"]` the status contains "SNAPSHOT" and the table still completes with 7,775 records; a `js` probe calling the plugin's exported age function with a date 13 days old returns a label containing "STALE". Acceptance on the day after merge: `gh api "repos/Ventusltd/globalgrid2050/actions/workflows/datacentre-news.yml/runs?per_page=5"` shows a run with `event` = `schedule`, and the branch has a commit from it. If no scheduled run appears, the schedule is the fault to chase before anything else.

## What this does not fix

The NEWS SIGNAL column stays empty for 7,746 rows. A live headline feed cannot fill it without name matching. The only exact, Ref-keyed signal available is the register change already in `events/register_changes.json` (274 projects), which updates when the REPD does. Pointing the column at that, with a link to the row's record, is a separate small change for the signal study.
