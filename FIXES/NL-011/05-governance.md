# NL-011 study 05: governance and authority

Lens: how authority moved through the link on 31 Oct to 2 Nov 2026. Covers who could instruct whom, what counted as
the owner's word, the ACCEPT rule, who merged, and who refused whom. Read-only study. Comment ids are on
Ventusltd/neural-link-between-agents unless another repository is named. Times are GitHub's own `created_at`/`merged_at`.
Scratch fetches: `gh api "repos/Ventusltd/neural-link-between-agents/issues/<n>/comments?per_page=100" --paginate`
for n = 1..10 (156 comments).

## Verdict

The ACCEPT rule held completely. No agent wrote an ACCEPT line. Two agents refused a relayed acceptance. Refusals
between agents carried measurements and changed outcomes. The merge rule did not hold. The harness merged and published
on chat authority on 31 Oct and again tonight: 4 PRs, 1 direct merge to kuiper-belt main and 1 hand-dispatched deploy.
NL-008 QA raised this as a MAJOR finding and asked the owner to decide. That decision was never recorded. The night's
own law (LAW.md 9.6) and the harness's plan (OVERNIGHT.md, GREEN.md) now disagree about who moves the pointer next.
Nothing technical can settle any of this. All four affected `main` branches are unprotected. Every comment, merge and
commit carries one GitHub login and one Claude session id. So "only the owner merges" can be neither enforced nor
audited, and the owner's own ACCEPT is proven only by circumstance.

## What to change (smallest rules that make authority unambiguous)

1. **Two identities.** Agents, the harness included, use a machine account or a GitHub App token with no merge right on
   `main` of gridatlas, kuiper-belt, globalgrid2050 and globalgrid2050-homepage. Branch protection then requires the
   owner's merge. This one change turns "agents never post ACCEPT" and "only the owner merges" from honour into
   fact, and makes `merged_by` and `user.login` mean something. If a second account is impossible, an owner act
   counts only as a commit or tag signed with a key agents do not hold.
2. **DELEGATION is its own message type.** Chat permission counts only after the harness posts `TYPE: DELEGATION`
   with these fields:
   - the owner's words verbatim;
   - ACTIONS (merge / publish / deploy / pointer);
   - REPOS;
   - GATES STILL BINDING;
   - RULES SUSPENDED, each as path:line;
   - EXPIRES, a UTC time.

   Anything not listed stays under the written rule. Each merge made under it cites the DELEGATION comment id in its
   commit or PR body.
3. **ACCEPT has an object.** `ACCEPT <stamp>` or `ACCEPT <path>@<sha>`. A bare "ACCEPT" accepts only the item it
   answers, and never implies merge or publish authority.
4. **Rulings go on the bus.** Before any harness decision that relaxes a gate, overturns a posted RULING or REVIEW, or
   transfers a role is acted on, the harness posts it on the issue as `TYPE: DECISION`. A subagent acts on a harness
   direct message only if it cites that comment id. Write "owner via harness" only with a verbatim quote and its
   source.
5. **An open question means the strict reading.** While an owner question that governs an action is open (Q6,
   NL-008 Q4, T5A decision 1), that action takes the stricter reading: draft PR, owner merges. A conflict between chat
   and a committed rule is raised as a `CONFLICT` BLOCKER (PROTOCOL.md:33), unless a DELEGATION names the rule.
6. **The gate comes first, and the merge proves it.** A merge commit or PR body names the gate run ids with their
   completion times, and every one must be earlier than the merge.
7. **One line in OPUS-BRIEF.** A tester's FAIL blocks the lead's HANDOFF, and a HANDOFF's STATUS is PASS or it is not
   posted.
